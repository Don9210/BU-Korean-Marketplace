만든 것은 조각(컴포넌트)과 DB 요청 함수입니다. DB 규칙은 기존 `supabase/schema.sql`을 그대로 씁니다.
새 패키지, 새 테이블, 새 SQL은 없습니다.

## 상세 화면(기능 4)에 끼우는 방법

상세 화면이 글(`listing`)을 불러온 뒤, 아래 한 줄을 넣으면 됩니다.
판매자에게는 상태 버튼이, 선택된 구매자에게는 "거래 확인" 버튼이 보이고, 그 밖의 사람에게는 아무것도 보이지 않습니다.

```tsx
<DealSection listing={listing} onChanged={setListing} />
```

판매자 정보에 평점을 보여 줄 때:

```tsx
<RatingSummary ratingAvg={seller.rating_avg} ratingCount={seller.rating_count} />
```

## 실제 BU 계정 2개 테스트 (로그인·댓글 기능이 준비된 뒤)

A = 판매자(일반 브라우저), B = 구매자(시크릿 창). 댓글 화면이 아직 없으면 담당자가 Supabase Table Editor에서
`comments`에 B의 댓글 한 줄(`listing_id`, `author_id`, `body`)을 직접 넣고 시작합니다.

| 절차 | 기대 결과 |
|---|---|
| A가 자기 글에서 예약중 → 판매중 | 상태가 바뀌고 새로고침 후에도 유지 |
| 댓글이 없는 글에서 A가 거래완료 | "아직 댓글을 단 사람이 없어요" 안내, 완료 불가 |
| B가 댓글을 단 글에서 A가 거래완료 → B 선택 | 상태 거래완료, "B 님의 확인을 기다리고 있어요" |
| B의 내 활동 | 확인 대기 거래에 그 글이 보임 |
| 확인 전에 A가 판매중으로 되돌림 | B의 확인 대기 거래에서 사라짐 |
| 다시 완료 처리 후 B가 "거래 확인" | A, B 모두 거래 완료 횟수 +1. 두 번 눌러도 +1만 |
| 확인 후 A가 상태 변경·글 삭제 시도 | 바꿀 수 없다는 안내 |
| A, B 각자 내 활동 → 평가할 거래 | 서로를 한 번씩 평가. 평가 후 목록에서 사라짐 |
| 평가받은 쪽의 내 활동 | 평균 평점과 평가 개수 표시. 평가 전에는 "아직 평가 없음" |
| 제3의 계정 C의 내 활동 | A·B의 거래가 보이지 않음 |

## 확인한 것과 못 한 것

- 확인: TypeScript·Vite 빌드, oxlint, 가짜 데이터(모의 API)로 폰 크기 화면에서 위 흐름의 화면 동작.
- 못 함: 실제 Supabase 로그인 상태에서의 저장·권한 검사. 인증 메일 설정이 끝난 뒤 위 표대로 테스트해야 합니다.
- DB 규칙 자체(구매자 지정 조건, 횟수 +1, 평가 1회 등)는 11-14에 테스트용 DB에서 따로 검사했습니다.
